## Critical rules (read first)

1. **Verify provider facts from current docs, never memory.** Model IDs, parameters, limits, prices, retirement dates, retention terms and regulatory dates decay within months; an unverified provider claim is `NOT VERIFIABLE` (see **Provider-fact caveat**).
2. **Everything that enters the context is untrusted data that may carry instructions** — user text, retrieved chunks, web pages, emails, files, tool results, tool descriptions. No privileged action may follow from it without a control outside the model.
3. **Model output is untrusted input to every sink** — HTML/markdown, SQL, shell, file path, URL fetch, deserialization, downstream API arguments. Encode, validate or sandbox it like user input.
4. **Bound everything** — steps, wall-clock, tokens, cost, retries, fan-out, tool-result size, retrieved chunks. Unbounded means an outage or a bill, not a feature.
5. **Eval before change.** A prompt, model, retrieval or tool-description change ships only with an eval delta against a baseline; "looks good on three examples" is not evidence.
6. **Irreversible or high-impact actions need a code-enforced human gate or an undo** — the approval shows the real action, and authority is the requesting user's, never broader.
7. **Authorization lives in code at the point of action, with the end user's identity.** Prompts, delimiters and guardrails are defense in depth, never the boundary.
8. **Project decisions outrank this doc** (config, ADRs, accepted trade-offs, provider contracts). Items marked `[LEGAL-OWNER]` are flagged and routed to a compliance owner — the reviewer never decides legality.

## §A Prompt & model contract (AE-1)

**Principle.** A prompt is code that runs on a probabilistic interpreter: version it, separate instructions from data, give output a machine-checkable contract, and keep model choice and parameters in one pinned, swappable place. Most production incidents in this area are silent — a truncated JSON, a retired model ID, a prefill that 400s on upgrade — so detection signals here are mostly missing branches.

| ID | Best practice | Bad practice | Detection signal | Source |
| --- | --- | --- | --- | --- |
| K-A1 | Prompts live in versioned template files or a registry with named variables, one owner and a change note; reviewed like code | Prompt strings inline in handlers, edited ad hoc, no history or owner | Multi-line literals passed to `system=`/`messages=`/`instructions=` inside business logic; no `prompts/` dir; prompt diff with no eval or test diff | CL-PE; OAI-PE |
| K-A2 | Instructions, retrieved docs, tool output and user input sit in separate labelled blocks (system/developer vs user roles, XML tags); untrusted tool or web content stays inside `tool_result`, never in `system` | Untrusted text (web page, email, RAG chunk, file) spliced into the system prompt or instruction area with no boundary | f-string/`.format`/`+`/template interpolation of `{user_*}`, `{doc}`, `{retrieved}` into `system` or above the task; system prompt built from a DB or user-editable field | CL-BP; CL-HANDLE; O-TOP |
| K-A3 | Instructions state task, audience, format, constraints and WHY; say what to do instead of long `NEVER` lists; negatives only for hard constraints | Vague one-liners ("be helpful and accurate"); prompt dominated by `NEVER`/`DON'T`; ALL-CAPS tool-trigger language | No explicit output format/length/audience; count of `NEVER`/`DO NOT`/`MUST` per prompt file; reviewer cannot say what a good output looks like | CL-BP |

| K-A14 | Model IDs and SDK params are checked against the provider lifecycle (active/legacy/deprecated/retired) in CI or at startup; retirement date and migration owner recorded; migration proven by eval | Retired or near-retired IDs still in code; nobody owns migration; IDs copied from training-era examples | Literals for retired or dated snapshots; no startup model-availability check; no deprecation calendar (verify against CL-DEPR/OAI-DEPR — dates in reports are as of 2026-09-30) | CL-DEPR; OAI-DEPR |
| K-A15 | Per-model capabilities live in ONE adapter: sampling params only where supported (low temperature for extraction, never assume 0 = deterministic), thinking/effort config, forced `tool_choice`, no assistant prefill on models that reject it, `thinking` blocks replayed unmodified; reasoning effort or adaptive-thinking mode is explicit, pinned config that is evaluated per setting (changing it can also invalidate the prompt cache), and reasoning output is never shown or stored as the user-facing explanation or audit record (K-G4) | `temperature=`/`top_p=`/`top_k=`/prefill/`thinking={...}` copied across call sites and models -> 400 on upgrade | `temperature=`/`top_p=` next to a newer model id; last element of `messages` has `role: "assistant"`; `thinking={"type":"enabled"...}` on models that reject it; provider params sprinkled at call sites | CL-DEPR; CL-ERR; CL-BP |
| K-A16 | On a model swap, prompts are re-tuned (old anti-laziness, aggressive tool-trigger and over-thoroughness text removed) and evals re-run | Prompt written for an older model copied unchanged | Model id bumped in the diff while prompt files are unchanged and no eval delta reported | CL-BP |

## §B Security & safety (AE-2)

**Principle.** Assume any text the model reads can carry instructions and that no filter reliably strips them (adaptive attacks broke published defenses at over 90% success [W-2]). Security therefore comes from architecture: break the lethal trifecta, give tools least privilege, enforce authorization in code, treat output as untrusted at every sink, and keep secrets and other tenants' data out of the context in the first place.

### The lethal-trifecta model (AE-2.3)

An agent path is exploitable for data theft when it combines all three legs: **(1) access to private data**, **(2) exposure to untrusted content**, **(3) an outbound channel** (network, email, links, markdown images, PR/comment creation, any side-effecting tool). Meta's "Rule of Two" says an agent session should hold at most two of untrusted input, sensitive access and external state change. Analyse tool COMBINATIONS, not single tools.

| Leg | Typical carriers | Ways to remove it |
| --- | --- | --- |
| Private data | Mailbox, repo, DB, files, memory, other tenants' rows | Scope retrieval to the caller before context (K-D11); read-only, per-session narrow scope (one repo, one folder) |
| Untrusted content | Web pages, inbound email, issues/PRs, uploads, RAG chunks, tool results, MCP descriptions, image or PDF text | Drop the ingestion source; quarantine it in a tool-less model returning typed values (K-B6); plan-then-execute so the plan is fixed before the untrusted read |
| Outbound channel | `send_email`, `http_post`, `create_pr`, `fetch_url`, image rendering, link click, write tools | Egress allowlist proxy; block remote images and links in rendered output (K-B22); hard human approval on the channel (K-C14) |

Break at least one leg per session or tool set; when a leg cannot be removed the design needs a hard approval gate and a documented residual risk.

| --- | --- | --- | --- | --- |

## §C Agent & tool design (AE-3)

**Principle.** Use the least autonomy that solves the job, then make every loop bounded, every tool least-privileged and model-usable, and every irreversible action human-gated or undoable. An agent's own claim of success is a hypothesis; verify against real state.

### Workflow-vs-agent ladder (AF-1)

| Rung | Shape | Use when | Controls it must carry |
| --- | --- | --- | --- |
| L0 | Deterministic code, rules, search, template | The steps or answer are computable without a model | Consider first; record why a model is needed |
| L1 | Single model call plus retrieval or examples | One transformation or answer; no branching decisions | K-A7–K-A12, K-E1–K-E7 |
| L2 | Fixed workflow (chain, route, parallelise, evaluator-optimizer) | Steps are predictable and can be enumerated in code | L1 controls plus per-step eval and K-F14 state assertions |
| L3 | Single agent loop with tools | Open-ended problem where steps cannot be predicted | L2 controls plus K-C2 loop budgets, K-C3 stuck detection, K-C14 human gate, K-C13 least agency |
| L4 | Multi-agent (orchestrator and workers) | Parallelisable, high-value, loosely coupled work (about 15x tokens per a 2025 vendor report; verify the figure) with a single-agent baseline that fails | L3 controls plus K-K1–K-K4 |

Choose the lowest rung that passes the eval, with a written reason (`AF-1`). Framework abstractions that hide raw prompts and responses raise change cost — keep a way to see them (AN-AGENTS).

### Loop budgets (AE-3.1)

| Budget | Required | Failure mode when absent |
| --- | --- | --- |
| Max iterations or turns | Every model loop | Runaway loop, denial of wallet |
| Wall-clock deadline (propagated to tool calls) | Every agent run and tool call | Hung threads, held cost |
| Token and USD cap (client-summed `usage`) | Every run; SDK budget options are advisory or checked only between turns | Cost cliff discovered on the invoice |
| Repeated-call detection (hash of tool plus canonical args, about 3x; A-B alternation; N consecutive failures) | Any loop with tool feedback | Same failing call retried dozens of times |
| Depth and fan-out cap for sub-agents and parallel calls | Any spawn or `Promise.all` over model calls | Unbounded recursion or amplification |
| Cap-hit behaviour | Explicit handled error or partial result, never silent truncation | Caller believes the task finished |

## §D Context & retrieval (AE-4)

**Principle.** Context is a budget, not a bucket: fill it with the smallest high-signal set, order it so the stable prefix caches, enforce authorization before retrieval rather than after generation, and make every grounded answer checkable. More tokens degrade recall at every length (context rot), and best evidence belongs at the start or end (ARX-LIM).

| ID | Best practice | Bad practice | Detection signal | Source |
| --- | --- | --- | --- | --- |
| K-D1 | Every context source (system, tools, history, RAG, tool results, output plus thinking) has a token budget measured via `usage` or a count API on the TARGET model (a tokenizer change alters counts) | Unmeasured prompts; counts reused across models; "just send everything, the window is 1M" | No tokenizer/`count_tokens`/`usage` logging; hard-coded char limits; model upgrade with no recount | CL-TOK; CL-CTX |

## §E Reliability & cost (AE-5)

**Principle.** Providers fail, throttle and refuse; users and loops amplify cost. Every call has a deadline, a bounded transient-only retry policy and a designed failure path, and every spend axis has a cap enforced before the call — a public endpoint that spends tokens without auth and quotas is a denial-of-wallet vulnerability.

## §F Evaluation & testing (AE-6)

**Principle.** Behaviour that is not measured regresses silently. Evals are the unit tests of probabilistic behaviour: built from real failures, run on every prompt, model, retrieval or tool change, and reported as a delta per slice. Deterministic glue around the model gets ordinary tests with the model mocked at one seam. Tests must name the business rule they protect and FAIL when it breaks — not mirror current prose.

| ID | Best practice | Bad practice | Detection signal | Source |
| --- | --- | --- | --- | --- |
| K-F1 | Every AI feature ships a versioned eval suite (dataset, task, scorer) run before merge; success criteria are written and multidimensional (task fidelity, safety rate, latency p95, cost per call, error severity) BEFORE building | Merged with manual "looks good" prompts; "good performance" or accuracy only | PR adds prompt, model or agent code with no diff under `evals/`, `tests/`, `*.eval.*`, `promptfooconfig*`, `.jsonl`; no scorer function; no criteria doc or threshold constants; latency and cost absent from eval output | OAI-EVALS; EY-PAT; CL-TEST |
| K-F2 | Start with 20-50 tasks from real failures (bug tracker, support queue, production traces) and grow by adding every incident; rows carry `source`/`trace_id`/`incident` | Only synthetic happy-path prompts; dataset never updated after incidents | Dataset has no `source`/`trace_id`/`incident` field; last-modified older than the prompt; no link from a bug fix to a new case | AN-EVALS; HAMEL-FIELD |

## §I Human experience (AE-9)

**Principle.** The interface is a control. It must set honest expectations, show sources and uncertainty only where they change a decision, let the user correct, undo or reach a human, and treat failure, refusal, empty and slow states as designed screens. "Human in the loop" is a design claim to verify, not a control by itself: reviewers drift to rubber-stamping (agreement with wrong AI advice is the most consistent outcome across studies — Tier-3 secondary summary of ARX-OVERSIGHT; EU Art 14 names automation bias). For visual identity and journey rules of the surface itself, the UI/UX gate applies (`UX-*`, `UI-*`, `DD-*`); report a defect once.

## §J RAG (conditional — only when a vector index or retrieval pipeline exists)

**Principle.** RAG is a pipeline of separately failing stages: ingestion, chunking, embedding, retrieval, reranking, context assembly and generation. Evaluate retrieval independently from generation, treat the corpus as an untrusted instruction carrier, and version, refresh and delete the index as a first-class data store. Authorization and tenant isolation at query time are K-D10–K-D12; grounding, citations and abstention are K-D13–K-D14 — apply them here too.

| ID | Best practice | Bad practice | Detection signal | Source |
| --- | --- | --- | --- | --- |
| K-J1 | Retrieval is evaluated on its own labeled query-to-relevant-doc set, separately from generation; track recall@k, MRR, nDCG and precision@k with k equal to the production `top_k`; failures are attributed to retrieve versus generate | Only an end-to-end answer score; cosine similarity of answers or ROUGE as the sole "RAG quality"; retriever, reranker, prompt and generator in one function with no seams | Eval computes only final answer quality; no retriever-only test; metric k differs from the retriever `top_k` | WEAVIATE-EVAL; HAMEL-FAQ; ARX-RAGAS |
| K-J2 | Generation metrics are separate: faithfulness or groundedness (claims supported by context), answer relevance and context precision (RAGAS-style RAG triad); the judge is calibrated (K-F17) | Fluent but unsupported answers; groundedness never measured | No faithfulness check in evals or at runtime; uncalibrated judge (confidence: medium-high) | ARX-RAGAS; O-LLM01 |
| K-J3 | Hybrid lexical (BM25) plus vector retrieval with fusion for names, ids and acronyms, measured against vector-only | Vector-only search for ID, SKU, error-code or legal-citation queries | Retriever calls only embedding search; no lexical index; eval lacks exact-identifier queries | EY-PAT; AN-CR |
| K-J4 | Retrieve wide (for example top 20-150), rerank, pass fewer best chunks; contextual retrieval plus BM25 plus rerank cut retrieval failures from 5.7% to 1.9% in a vendor benchmark (confidence: medium) | Naive top-3 or top-5 from a single embedding pass; no reranker evaluation | `top_k=3` hard-coded, no rerank stage, no measured recall at the candidate stage | AN-CR |
| K-J5 | Chunk size, overlap and strategy are chosen by measured retrieval on the project's own corpus; structure (headings, tables, code) preserved; chunk context (doc title, section) added | Framework-default chunking never tested; context-free chunks ("revenue grew 3%"); splits mid-table or mid-sentence | `chunk_size=`/`chunk_overlap=` constants with no eval reference; chunks lack doc or section metadata | CHROMA-CHUNK; AN-CR; WEAVIATE-CHUNK |
| K-J6 | Embedding model name, version, dimension and metric are recorded in index metadata and per vector; a model change means a full re-embed into a new index or namespace, shadow eval and cutover; query and documents use the same model (confidence: medium — consistent practitioner sources, no vendor spec) | Swapping the embedding model or SDK default for queries only; mixing vectors from two models in one index -> silent nonsense retrieval | Embedding model id unpinned or `latest`; no `embedding_model` metadata field; model change in the diff with no index change or reindex script | FORMATION; TIANPAN-EMB; RAGABAST |

| K-J8 | Source deletion, redaction and erasure propagate to vectors, chunk text, caches and eval or few-shot sets (mark unavailable first, then delete, verify); chunk-to-doc id mapping exists (see K-H7) | Deleting the source leaves orphan chunks retrievable; tombstones never compacted | No delete path in ingestion; no test that a deleted doc is unretrievable; no chunk-to-doc mapping | ORACLE-DRIFT; PARAGON-FRESH |
| K-J9 | Retrieved text is untrusted: delimited, never obeyed as instructions; ingestion sources validated and provenance-tracked; who can write to the corpus is reviewed; hidden text stripped; least-privilege tools when RAG context is present (five injected documents reached about 90% attack success in PoisonedRAG) | Anyone (public web, uploads, tickets, wiki) can write into the corpus feeding a privileged agent; retrieved text can trigger tool calls | Ingestion accepts arbitrary URLs or uploads into a shared namespace; retrieved text concatenated raw into the system or instruction position; no injection test with a poisoned chunk | ARX-POISONED; USENIX-POISONED; O-LLM08; O-LLM01 |
| K-J10 | Embeddings are treated as sensitive (they can be inverted): classify and redact PII before embedding where feasible; same access control, retention and encryption as the source; vector DB requires authn (confidence: medium) | Raw PII or secret documents embedded into a shared store "because vectors are not readable"; vector DB exposed without auth | No PII classification or redaction at ingestion; vector store open to broad roles; vector DB port open or no auth in compose or Terraform; API key in client-side code | O-LLM08; O-LLM02 |

## §L Fine-tuning, classical ML, model supply chain & AI-assisted code (conditional)

**Principle.** Classical ML fails through leakage, unrepresentative splits and unmonitored drift; the model and package supply chain fails through unsafe file formats and unverified names; AI-authored code fails the same review bars as human code. Each is a data or artefact-integrity question, not a prompt question. Multimodal and voice features reuse the rows below plus the notes at the end of this section.

| ID | Best practice | Bad practice | Detection signal | Source |
| --- | --- | --- | --- | --- |
| K-L1 | Split FIRST; fit scalers, encoders, selectors, imputers, target encoders and embeddings only on the train fold (sklearn `Pipeline`); no features derived from the label or post-outcome data; entities (patient, user, session, document) kept whole via group splits; dedupe across splits | `fit_transform(X)` on all data then `train_test_split`; `SelectKBest` before the split; the same user in train and test; a feature computed from a future or outcome column | `fit_transform(`/`fit(` before `train_test_split`/CV; `train_test_split(` without `groups` on grouped data; features named `*_after*`/`*_outcome*`/`is_churned_*`; suspiciously high CV (over 0.99) | SKLEARN-PIT; SKLEARN-CV |
| K-L2 | Time-dependent data is split by time (`TimeSeriesSplit` or a train-before, test-after cutoff); features computed as of prediction time; label maturity respected | Random `KFold(shuffle=True)` on time-ordered data; rolling features that peek forward | `shuffle=True`/default `train_test_split` on frames with a date column and no `TimeSeriesSplit`; `.rolling(...).shift(-n)`; `center=True` rolling | SKLEARN-CV |

## Anti-pattern gallery — the most common bad practices, each with its fix

| # | Bad practice | Fix | K-id |
| --- | --- | --- | --- |
| 1 | Model output flows into `eval`/`exec`/shell or a raw SQL string | Structured tool call plus parameterized query, or a disposable sandbox | K-B20, K-B21, K-K5 |
| 2 | User, web or retrieved text spliced into the system prompt | Separate roles and labelled blocks; untrusted text stays in user or `tool_result` content; controls in code | K-A2, K-B3 |
| 3 | "The prompt says never do X" is the only guard on a destructive action | Code-enforced permission or approval at tool execution | K-B3, K-C14 |
| 4 | One agent has private data, untrusted input and an outbound channel | Remove a leg: quarantine, per-session scope, egress allowlist, approval | K-B1, K-B6 |
| 5 | `while True` agent loop, no step, time or cost cap | Iteration, deadline, token and USD caps plus repeat detection and a handled cap-hit result | K-C2, K-C3 |
| 6 | Tool takes `user_id`/`tenant_id` from the model and trusts it | Derive identity from the authenticated session; authorize in the handler | K-C10 |
| 7 | Vector search with no ACL filter, or filtering after generation | Tenant and permission filter in the query from server-side identity; cross-tenant test | K-D10, K-D12 |
| 8 | "Reply in JSON" plus `json.loads`, or regex on prose | Provider structured output or strict tool use, schema plus semantic validation, bounded retry | K-A7, K-A10, K-A11 |
| 9 | Ignoring `stop_reason`/`finish_reason`; refusal parsed as data | Branch on truncation, refusal, tool_use, pause; count the reasons | K-A8 |
| 10 | Floating or scattered model ids; retired ids; params copied across models | One config module, pinned ids, capability adapter, lifecycle check in CI | K-A13, K-A14, K-A15 |
| 11 | Prompt or model change merged with no eval | CI eval with baseline delta per slice and threshold | K-F4, K-F5 |
| 12 | Eval rows copied into few-shot examples | Dev and held-out split; containment check between eval set and prompts | K-F8 |
| 13 | An uncalibrated LLM judge as the sole quality or safety gate | Human-labeled calibration (TPR and TNR), different pinned judge, deterministic checks first | K-F17, K-F19 |
| 14 | Auto-approve flags, or approval of a model-written summary | Approval shows real action, args and diff; risk-rated tools; no default "Approve" | K-C14, K-C15 |
| 15 | Retry on every exception, stacked SDK and app retries, retrying spend-cap 429 | Transient-only, backoff plus jitter, one retry layer, honour `retry-after` | K-E2, K-E10 |
| 16 | No `max_tokens`, no quotas, unauthenticated LLM endpoint | Per-call caps, per-user and tenant budgets before the call, auth, spend alerts | K-E7, K-E8 |
| 17 | Whole DB rows or records in the prompt; PII to a provider unredacted | Field allowlist, redaction, provider terms checked | K-D9, K-B11 |
| 18 | Chat UI auto-renders remote images or links from model output | Allowlist or proxy images and links; sanitize markdown; CSP `img-src` | K-B22 |

## Provider-fact caveat

Model IDs, parameters, limits, prices, retention terms, deprecation and retirement dates, protocol revisions and regulatory dates change on a scale of weeks to months. Every numeric or named provider fact in this catalog (limits, discounts, minimums, counts, model or tier names), dated or not, was true at 2026-09-30 at best and is a prompt to verify against current provider docs, never evidence.

| Fact class | Verify against |
| --- | --- |
| Model IDs, aliases, retirement and deprecation dates, API parameter deprecations | CL-DEPR; CL-MODELS; OAI-DEPR |
| Sampling, thinking, forced `tool_choice`, prefill, schema-complexity limits per model | CL-DEPR; CL-ERR; CL-SO; the provider's migration guide |
| Context windows, tokenizer counts, cache minimums, TTL and multipliers, batch discount | CL-CTX; CL-TOK; CL-CACHE; OAI-CACHE; CL-BATCH |
| Rate limits, retry semantics, spend-cap responses | CL-RATE; CL-ERR |
| Data retention, ZDR and training eligibility per feature | CL-RETENTION; OAI-DATA |
| Prices | The provider's current pricing page |
| Protocol and standard revisions (MCP spec, OTel GenAI conventions, OWASP lists) | MCP-SEC; MCP-AUTH; OTEL-ATTR (development stability — pin the version); O-TOP |
| Regulatory dates and thresholds (EU AI Act, CCPA/ADMT, GDPR case law) | Official Journal and regulator pages; EU-IMPL as a secondary index; `[LEGAL-OWNER]` decides |

**How to verify:** (1) fetch the provider's official page (WebFetch or WebSearch) and cite the URL and date; (2) use a documentation-retrieval tool such as context7 when available for SDK and library behaviour; (3) never take a model ID, parameter, limit or retirement date from memory, from a blog snippet or from the code under review. **Unverified means `NOT VERIFIABLE`** — say so in the report; do not raise a finding that a model is retired or a parameter is unsupported without a current source, and do not approve one on the same basis.

## Glossary

| Term | Meaning |
| --- | --- |
| Lethal trifecta | Private-data access plus untrusted content plus an outbound channel in one agent path — the condition for data exfiltration by injection |
| Indirect prompt injection | Instructions hidden in content the model reads (web page, email, RAG chunk, tool output, image text) rather than typed by the user |
| Rule of Two | Design rule: a session holds at most two of untrusted input, sensitive access and external state change |
| Spotlighting | Delimiting, labelling or encoding untrusted content to help the model separate it from instructions; defense in depth only |
| Dual-LLM / CaMeL | Privileged planner never reads untrusted text; a tool-less quarantined model returns typed values under data-flow policies |
| Excessive agency | An agent holding more tools, permissions or autonomy than the task needs (OWASP LLM06) |
| Denial of wallet | Cost or quota exhaustion through unbounded input, loops or fan-out (OWASP LLM10) |
| Tool poisoning / rug pull / shadowing | Malicious MCP tool descriptions; a server changing its manifest after approval; one server's descriptions steering another server's tools |
| Slopsquatting | Registering package names that models hallucinate so an unwary install runs attacker code |
| Context rot | Recall degrading as context grows even when all content is relevant |
| pass^k | Probability that all k trials of a task succeed; a reliability metric next to pass@k |
| LLM-as-judge | A model grading another model's output against a rubric; needs human calibration |
| Faithfulness / groundedness | Share of answer claims supported by the retrieved context |
| Sink | Any consumer of model output (renderer, database, shell, URL fetch, file, API) |
| Automation bias | Reviewer deference to an AI verdict, producing rubber-stamp oversight |
| ZDR | Zero data retention terms at a provider, usually eligibility-limited by feature and model |
| AI-BOM | Inventory of models, datasets, adapters, prompts, tools and vector stores with versions, hashes and licences |
| ADMT | Automated decision-making technology, regulated under CCPA rules and GDPR Art 22 |

## Closing reminders

- **Verify provider facts from current docs** — an unverified model ID, parameter, limit, date or price is `NOT VERIFIABLE`, never a finding or an approval.
- **Untrusted in, untrusted out** — every input to the context may carry instructions and every output is untrusted at every sink; the boundary is code with the end user's identity, not a prompt or a guardrail.
- **Bound everything and eval every change** — steps, tokens, time, cost, retries, fan-out; no prompt, model, retrieval or tool change without an eval delta, trace and kill switch.
- **Human gate or undo for irreversible actions**, and route `[LEGAL-OWNER]` questions to the compliance owner rather than deciding them.
- **Project decisions outrank this catalog**; cite `file:line`, the clause and the checklist check id for every finding (a `K-` id only as the rationale pointer), take severity from the checklist, calibrate with `.claude/docs/ai-engineering-calibration.md`, and never invent a measurement.
