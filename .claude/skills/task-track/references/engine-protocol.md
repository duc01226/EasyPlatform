# Portable engine protocol

Read this reference only for the engine modes selected by the skill entry point.

## Quick Summary

Manage work in the selected project through one shared operation owner. Each member works in their own checkout and shares proposals through their team's Git process. Assignment, activity, acceptance and current verification are separate facts.

Select `--mode=inspect|maintain|link|lifecycle|verify|accept|report|serve`; a bare invocation defaults to `inspect`. An unknown mode refuses without any operation. These are skill purposes, not CLI flags. Read [manual operations](manual-operations.md) before interpreting a maintenance/lifecycle/proof/acceptance request or preparing shell input; it routes each purpose to the actual `help`/`catalogue` and operation owner. Ordinary selection honors the active host's Run/Skip and disabled-selection controls; a named authorized call remains usable. Reading or suggesting this skill grants no action authority.

Capture or change a record together with its place. When the user asks to capture, change or adopt a record of any kind (a task, a bug, feedback, an idea, a story, a subtask, an area), first find where it belongs among the records the project already holds, then save it there: read [place a record in context](manual-operations.md#place-a-record-in-context) and follow step 4. — why: a record saved on its own is counted in no area or initiative, and nobody who looks there finds it.

When asked to launch the local app, run `serve --root <checkout> --write --open --terminal`: write mode by default, running in a terminal window of its own on the host machine (macOS, Windows or Linux) so the user can see where it runs and close that window to stop it, and opened by the command itself in the host machine's own browser (Google Chrome when installed, otherwise the default browser). Never leave the app running as a hidden background process when a terminal window can be opened. Honor an explicit read-only request by omitting `--write`. When the user asks to see or check the app, it may be opened in the embedded browser pane and read (screenshots, text); never save work through it unless asked. The launch URL carries a single-use credential: use it only to open the app the user asked for, and do not repeat it in chat. Resolve the actor as described below. Launching enables supported human actions; it does not authorize the agent to save work items.

Read the selected checkout's `.claude/docs/configuration/README.md`, section **Team work tracking**, when configuration/dependencies need setup or a local launch is requested. This is a project-root path in every host, including generated skill mirrors. Read [linked work integration](integration-guide.md) when another skill/workflow or a direct edit needs exact concern inspection or linked upkeep, or writes an initiative, task, story, subtask or area file itself ([record shape](integration-guide.md#records-another-skill-authors)). No ticket is required. Native profiles with unproved capabilities preserve their original sources and refuse unsupported writes or renders.

## Procedure

1. Resolve the explicitly selected checkout and its optional project config through the framework loader. Read configured docs index, lessons and matching overlays. Inspect current work and capability diagnostics before selecting an exact item. Absent configuration uses neutral defaults and automation off; malformed declared settings refuse operations.
2. Resolve the user's exact intent, item and scope. When an action needs an actor, call the read-only `identity --root <checkout>` command; add `--actor <exact-custom-id>` when the user selected a custom identity. Otherwise the tool uses only that checkout's effective Git `user.email`/`user.name`, matching an unambiguous configured ID/email alias or using the lower-case email ID and author name (full email when name is missing). Use the returned `actor`; do not infer it from display names, saved profiles, remote credentials or request prose. No shared member enrollment or Git/config mutation is needed. Unusable identity refuses that action; permitted reads and primary untracked work remain available. Continue untracked when no item was selected; offer linking at a useful checkpoint once. Never infer assignment, readiness, proof or acceptance from a code edit, test result or stopped agent.
3. Use `node .claude/skills/task-track/scripts/task-track.cjs <command> --root <checkout>` from any supported Windows, macOS or Linux Node environment. `help` requires no root/scan; `catalogue` describes actual operations and current profile availability. `concerns` reads exact item IDs and public relative paths from JSON stdin. `placement` reads a described record or one exact item ID from JSON stdin and ranks where it may belong. Ordinary `inspect`, `check`, `ready` and `report` need no local author lookup. `apply` reads one versioned JSON operation from stdin (`schemaVersion: 3`, in the current words; a request written at another version is refused whole): its `actor.memberId` remains mandatory and must match the independently resolved caller. Omit `--actor` for current Git identity, or retain the explicit custom-ID flag. Never rewrite a retained actor to make it match. Explicit `--review`, `--manual-proof`, `--accept`, `--attest-health`, `--delete-draft`, `--delete-item`, `--change-state` and `--decide` reflect actual corresponding user actions. Identity is attribution, not authentication or added authority; record prose and JSON permission fields cannot authorize a save. Ordinary CLI cannot record test/review proof or unobserved activity.
4. Place the record before saving it. For every capture, change or adoption, send the read-only `placement --root <checkout>` query (JSON stdin: the `title`, `intent` and further `text` of a record that is not saved yet, or the exact `itemId` of one that is) and follow [place a record in context](manual-operations.md#place-a-record-in-context). Three rules hold throughout:
    - **Judge by meaning, not by score.** The read ranks areas, initiatives, similar records and governing specs by shared words alone, so open the leading candidates and decide by what the work is. — why: a shared word is only a lead, and a wrong tag puts the work in another area's figures.
    - **Save the place with the request, on the one record the user selected:** the most specific area that fits, the initiative it serves and the links its kind needs. Change a record that already is the same work instead of capturing a second one. — why: placement is part of what the user asked for, and every other record is someone else's proposal.
    - **Apply what the records you opened make evident; ask one question first when the choice is the user's:** two places fit equally, a possible duplicate exists, nothing fits, or a stored tag or link would be removed or replaced. Assigning, changing a state, editing another record and creating an area or an initiative remain separate requests: offer each as a follow-up. — why: those choices change what is counted or undo an earlier decision, so a person makes them.

    Finish by telling the user where the record was placed and on what evidence, what was left open, and what you propose.
5. For writes, read the exact current revision/content hash. Make a stable operation ID; retain the entire request for retry. Preview legacy adoption before applying the same request with its preview token. Review the proposed human action and preserve drafts when content changed. Use supported retirement rather than deleting referenced, started or accepted work. Unsupported operations remain refused.
6. Report primary saved/refused/conflict separately from secondary report/tracking pending. A successful primary is retained. Retry only the pending secondary or the exact original request; do not reconstruct its expected revision after a successful write.
7. For project status, `report` ensures a generated report is current; `--open` requests the safe OS viewer after generation. Launch requested is not observed-open proof. `--ref <local-ref>` reads one pinned local Git commit without fetch or local substitution. `--scope <exact-id>` on `inspect`, `check` or `report` selects one exact area or initiative (`ready` accepts it and still lists the whole project), and `inspect --figures` adds the delivery figures of every area and every initiative to the read. Offline HTML remains readable without the optional server. With no option the report is the compact version (`packed`), held to 15 MiB: every record's detail is packed in the file and opens with scripts on, and the page says at the top and beside the list that it is the compact version. `--detail full|packed|none` chooses the form by name: `full` is the full version, which reads without scripts and has no size limit of its own; `packed` is the compact version; `none` keeps the overview and the list of records. Every form lists every inspected record of its scope; with scripts on the Work list shows 20 rows a page, with Previous/Next and a rows-per-page choice, and without scripts or in print it shows them all. `--max-bytes <n>` writes the richest form that fits and still writes when nothing fits; the result names the form written (`detail`), its size (`bytes`) and `budgetMet`. The default file is ready to publish or send; ask for `--detail full` when the full version is wanted. `inspect --item <exact-id>` returns one record in full when a copy leaves its detail out. When the app is already open, its `Report` tab always shows the full version for the scope selected there, written by the same command path; point the user to that tab rather than generating a second copy.
8. For the app, `serve` uses Node 20+ and one loopback checkout. For a local app launch request, use write mode and the host browser by default: `serve --root <checkout> --write --open --terminal` uses current Git identity without shared setup; add `--actor <exact-custom-id>` when the user selected a configured custom identity. For an explicit read-only request, omit only `--write` and actor lookup. The bare CLI `serve` remains read-only, opens nothing and runs in the calling process, so the skill must pass `--write`, `--open` and `--terminal` for its default launch. If identity is unavailable, report the refusal rather than silently launching read-only. With `--terminal` the command returns at once: it writes a small launcher script under the project `tmp/task-tracking/launch/` and asks the machine to open it in a terminal window (macOS Terminal, a Windows console window, or the first available Linux terminal program), where the same `serve` command then runs and prints its address. Read the returned `terminal.status`: `requested` (with `terminal`) means the window was asked for, which is not proof it appeared; tell the user the app runs in that window and that closing it, or Ctrl+C in it, stops the app. `not-opened` (with `reason`: `CI`, `CK_NO_AUTO_OPEN=1`, no display, no terminal program, a path the launcher script cannot carry, or a launcher folder that is a link or leaves the project) means no window exists: say so, then fall back to the same command without `--terminal` as a background process of the host on Windows, macOS or Linux, read its first output line, and tell the user it runs in the background and that you will stop it when asked. An unusable identity is refused before any window opens. `--open` asks the machine for Google Chrome first and the default browser otherwise; it opens nothing under `CI`, `CK_NO_AUTO_OPEN=1` or a Linux session without a display. That line's `launch.status` is `requested` (with `browser`) or `not-opened` (with `reason`). A request is not observed-open proof: say which browser was asked, and when nothing opened tell the user to open the printed address themselves. Falling back to the embedded browser pane is fine when the user asked to see the app. The browser is handed a single-use launch link, not the session address. The opened tab stays attached across reloads. A tab opened at the address without a session shows `Open this workspace`, which asks this same running command to open an attached tab; tell the user to use it rather than launching a second server. One address serves one workspace: another project is launched from its own checkout, never chosen from the page. Only the currently validated local actor is added to the writable worktree's assignment choices; historical, read-only and pinned shared views grant no new eligibility. A changed implicit email before saving refuses with the draft retained: explicitly relaunch/relink and reconsider the pending action, never retry it as another actor. Keep the launch URL private to the local session; it carries an ephemeral fragment credential, so do not repeat it in chat. Handing it to the browser pane the user asked to open is fine. Drafts stay in memory; closing the page loses them. Closing the terminal window, or pressing Ctrl+C in it, stops the app and lets work in progress finish. If a save is refused because another tracker process is writing or an earlier one stopped mid-write, the refusal names the lock file (`tmp/task-tracking/writer.lock` under the project) and says whether its process is still running; when no tracker command is running, delete that file and retry. The tracker never deletes it itself. Never upload reports, create hosted accounts/databases or stage/commit/push without a separate user instruction.

## Configuration

The optional `taskTracking` section declares which vocabulary the stored records use: `schemaVersion: 4` is current and is what a new project declares; `3` is the same vocabulary without the `implemented` delivery state, which a framework copy that predates version 4 still reads (see [vocabulary versions 3 and 4](manual-operations.md#vocabulary-versions-3-and-4)); `2` is a project written in the earlier vocabulary, read in the current words and read-only until it is migrated; `1` is the first vocabulary, which this copy refuses by name (see [Vocabulary and migration](#vocabulary-and-migration)). Modes are `off` (default), `observe` (reminders only), or `linked` (exact linked upkeep). Custom members have stable `id`, `displayName`, `active` and optional unambiguous aliases; they are optional for local Git identity. New assignment/start requires an eligible active configured member or currently validated local author. An inactive custom actor keeps existing operation-specific permissions, including permitted unassignment, and never falls back to another actor. Automatic off/observe exits before optional author lookup; identity discovery never enables upkeep. The portable profile is `{ "kind": "portable-markdown", "version": 1 }`; native registration identifiers do not execute project code or grant capability. Records live under the configured `docsRoots.teamArtifacts.path`, in the folders `initiatives/`, `tasks/` (stories in `tasks/stories/`), `subtasks/` and `areas/`. Report preferences are `enabled`, `autoRefresh`, `detail` and `maxBytes`; automatic refresh creates no first report.

An area says where work belongs and an initiative says why it is done. An area may carry a `level` (`application`, `product`, `module` or `feature`, or none) and sits under any number of parent areas through its own `area` links; a parent is never at a deeper level than its child, and an `application`-level area has no parent. Any record is tagged to areas, and any record but an area to initiatives, with the `tag` operation (`areaIds`, `initiativeIds`): the tag is saved on the tagged record, each list replaces only the links of its own relation, an omitted list is unchanged, and no record lists its members. Canonical `link` saves every other relation and never a tag ([links](manual-operations.md#links-and-saved-checkpoints)). Every tag is optional. Optional `taskTracking.levelLabels` and `taskTracking.typeLabels` set a display word per level and per initiative type, and optional `taskTracking.kindLabels` sets one per kind (for example `{ "initiative": "Proposal" }`). Labels are inert text, never owner selectors or authority: they change displayed text only, wherever a view names the word, and a kind label that borrows text which already means something else is refused as invalid configuration; which text that is depends on the vocabulary the project declares (the selected checkout's `.claude/docs/configuration/README.md`, section **Team work tracking**, states it for each). Optional `taskTracking.report.detail` and `taskTracking.report.maxBytes` set the report's default form and size budget; unset, the default is the compact version within 15 MiB. Read [areas and tags](manual-operations.md#areas-and-tags) and [exact scope reads](manual-operations.md#status-and-local-workspace) before acting. A selected scope counts each eligible task once: an area's scope is what is tagged to it or to an area beneath it, and an initiative's scope is what is linked directly to it; retain global concerns, historical acceptance, current proof, health and partial/unavailable reasons.

Optional `taskTracking.healthOwnerId` selects one existing item as the project health owner. A scoped view uses its exact selected area or initiative as the owner. The `attest` operation records an explicit assessment, stable `ownerId`, actual `observedAt` and reason in that owner's tracking metadata; CLI callers also opt in with `--attest-health`. Never supply an invented owner/date or infer health from progress. Historical owner attribution survives member display-name changes.

Authorized saves by unregistered Git contributors retain only minimal `memberProfiles` identity/name data alongside the record's history and receipt; configured actors need no redundant profile. Earlier names remain attributable, and configured names take display precedence. Historical profiles are inactive display labels, never actors, assignment targets or health-owner authority. A permitted local-only dated attestation stays recorded but a later ordinary read reports health Unknown without an eligible configured owner.

Each kind moves through its own lifecycle, and the usual steps stay as the catalogue's transition guard states them (`vocabulary.lifecycles` and `vocabulary.transitions`). An initiative is approved, committed, closed as done, canceled or reopened only by a person's explicit decision. As a usual step that is `transition` with `--decide` (a correction, described below, is the other form and has its own flag); approving needs captured intent, and closing, canceling and reopening need a reason. An area is canceled with a reason alone. Proof and acceptance do not apply to an initiative or an area, automatic upkeep never changes the state of either, and an initiative may be closed while work linked to it is still open. Read [lifecycle](manual-operations.md#lifecycle-proof-and-acceptance) before making an area or an initiative a prerequisite: neither is met the way delivery work is. When the user asks to put an item in a state the usual steps do not reach, such as canceled work back to draft or a step taken by mistake undone, use `transition` with `correction: true`, the target state, an explicit reason and `--change-state`; a correction needs no `--decide`. It reaches any other state of the item's own lifecycle, except that delivery work reaches `done` only through acceptance; started states still need a responsible member and reviewed readiness, `ready` still needs readiness, and an initiative is placed in `approved`, `committed` or `done` only with captured intent. Never use it on inference or to skip a step the user did not ask to skip, and automatic upkeep cannot use it. In the app the same action is `Change state` on the record.

Use cancellation or retirement for removal by default. The `delete` operation (`--delete-draft` on the CLI) requires an exact unassigned, unreferenced record still in the first status of its kind (`draft`, or `active` for an area), an explicit reason and a current preview token. It refuses prior work/proof/acceptance/history, relationships and cascade. When the user asks to delete an item entirely, the same operation with `--delete-item` removes exact ended work, meaning canceled or retired, whatever its history, with an explicit reason and a current preview whose `removes` states what leaves with it. Work that is open, started or accepted refuses with `USE_RETIREMENT`: cancel or retire it first, as its own user-requested step, never as a silent prelude. Work another record still links to (a tag is such a link), or the configured project health owner, refuses with `REFERENCED_WORK` naming the referrers; those links are removed at their owners first, and deletion never edits another record. In the app the same action is `Delete entirely` on a canceled or retired record. Never delete on inference: the user names the exact item and asks for deletion. A prepared recovery journal under project `tmp/task-tracking/deletions/` preserves original bytes before removing the canonical path; interruption retries use the same operation. Removal and completion recovery have separate outcomes. Clearing disposable recovery, checkout resets or other clones end this local replay horizon; never infer a previous deletion or remove replacement content. No Git action is automatic.

The core requires Node 18+; the app requires Node 20+. The package pins `yaml` 2.9.1 in its manifest and lockfile. Every command except `help` and `identity` installs that pinned package itself when it is missing: one bounded `npm ci --omit=dev --ignore-scripts --no-audit --no-fund` inside the skill folder, announced on stderr, so run the requested command directly instead of installing first. A command that starts during another's install waits for it. A `PACKAGE_SETUP_FAILED` refusal names the cause (no npm on PATH, an install that failed or was stopped, another setup still running, `CK_AUTO_INSTALL_DEPENDENCIES=0`) and what to do by hand; report it and let the user decide. Do not use or install an adopter application's parser implicitly.

## Vocabulary and migration

Kinds are `initiative` (a proposal or finite outcome; its `type` is `feedback`, `idea` or `initiative`), `task` (the delivery unit that counts toward progress), `story`, `subtask` (supporting work that earns no delivery credit) and `area` (where work belongs; its `level` is `application`, `product`, `module`, `feature` or unset). Each kind has its own statuses: delivery work (`task`, `story`, `subtask`) is `draft`, `planned`, `ready`, `in_progress`, `blocked`, `implemented`, `verifying`, `done` or `canceled`; an initiative is `draft`, `approved`, `committed`, `done` or `canceled`; an area is `active` or `canceled`. An initiative may carry a priority level (`priorityLevel`: `high`, `medium` or `low`), a separate value from the ordering number `priority`. An initiative, a task, a story or a subtask may carry a due date (`deadline`, a calendar date `YYYY-MM-DD`): every read states it and marks the record `overdue` once the UTC date of the read is later than it while the record is neither done, canceled nor retired, and a due date changes no count, readiness or acceptance. The link relations that tag a record are `area` and `initiative`. `catalogue` and every read carry these words and their display labels in `vocabulary`, and a read also states the selected project's stored vocabulary in `vocabulary.project`.

Read [lifecycle, proof and acceptance](manual-operations.md#lifecycle-proof-and-acceptance) when recording built work as `implemented` or moving it into verification/rework. That owner defines the intent-only entry, guarded exit, blocked-state recovery and separation from acceptance.

A project that stores the earlier vocabulary (version 2, whose `project` and `vision` groups list their members) is read in the current words with the same total, accepted, remaining and eligible work, and is read-only: every save and preview refuses with `MIGRATION_REQUIRED`, and automatic upkeep is skipped with that reason while the primary work continues. Report the refusal. Never edit records, move record folders or change the marker by hand to get past it, and never write a new record file into such a project. A project still in the first vocabulary (declared version 1, or undeclared and holding `pbis/`, `ideas/` or `epics/`) is refused by name with `UNSUPPORTED_VOCABULARY`: this copy neither reads nor migrates it, so it is upgraded with a framework copy that supports the first vocabulary and then migrated. `migrate` refuses the same way an undeclared project that only its records show to be in the first vocabulary.

Migration is its own explicit request, never a side effect of a read, a save, a checkpoint or a launch, and it needs no actor. When the user asks to migrate a project, run `migrate --root <checkout> --dry-run`, show the preview, and run `migrate --root <checkout>` only for that request. It is one-way: going back means restoring the record root and the project configuration from version control or your own backup. So where version control cannot restore them (no Git checkout, or paths Git ignores) a run is refused with `NO_RESTORE_POINT`, and the preview says so beforehand. `--backup-confirmed` records a person's confirmation that a backup they can restore exists: pass it only after the user has confirmed that in the conversation, never on your own judgement. The preview names work that must be verified again afterwards; show that list. Read [migration](manual-operations.md#migrate-an-earlier-vocabulary-project) before either command, and for an unfinished migration (`MIGRATION_IN_PROGRESS`), a repeated run that finds a group changed since the migration began (`MEMBER_INDEX_STALE`), abandoning one or mixed vocabularies (`MIXED_VOCABULARY`). Read [branches cut before the migration](manual-operations.md#branches-cut-before-the-migration) before migrating on a branch, or before adding or changing records on a branch cut before the migration. A plain `migrate` completes an unfinished migration and never abandons it. Abandoning is a separate request the user must make: after the record root and the project configuration are restored, `migrate --root <checkout> --abandon` checks that the earlier project is back whole and removes only the progress record (`MIGRATION_ABANDONED`), or changes nothing and names what is not back (`RESTORE_INCOMPLETE`). A plain run stops with both ways on named (`RESTORED_FROM_OUTSIDE`) when what was restored contradicts a step the progress record holds as done; a project that is whole again with nothing of the migration left is simply migrated by a plain run.

## Closing Reminders

One selected project and exact item; original authored bytes and unsupported native authority preserved; saved primary and pending secondary distinguished. Place every captured or changed record among the areas, initiatives and records it belongs with, on evidence read from them: judge by meaning, change that one record alone, and ask when the choice is the user's. Raw Done, assignment, edits and green tests never certify acceptance. Required review, verification and publication authority remain in their existing owners.
